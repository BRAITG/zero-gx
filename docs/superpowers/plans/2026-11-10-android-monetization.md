# Android Monetization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add silent bottom banners and a permanent Google Play ad-removal purchase without restricting free gameplay or ordinary source builds.

**Architecture:** One project-owned Kotlin plugin handles BillingClient, UMP, and the native banner view. A Godot autoload coordinates verified ownership and shared safe-frame chrome. The existing Worker verifies and acknowledges purchases using its existing Google service account; no new paid service, account system, or database is needed.

**Tech Stack:** Godot 4.7.2, Kotlin 2.1.21, Android Gradle Plugin 8.6.1, Gradle 8.11.1, JDK 17, Android API 24 minimum/API 36 compile and target; GMA Next-Gen 1.6.0, UMP 4.0.0, Play Billing 9.1.0; existing TypeScript/Vitest/Cloudflare Workers stack.

**Spec:** `docs/superpowers/specs/2026-11-10-android-monetization-design.md` (user-facing design approved; the explicit minor-privacy defaults, revocation codes, and release preflight clarifications accompany this plan for review).

## Review Focus

1. An old Play query or verification response arrives after a newer purchase, account refresh, or cancellation: it must not reverse current ownership. Pin in Task 3.
2. A successful purchase acknowledgement times out or races a restore: retrying the same token must neither consume it nor invent success. Pin in Task 1.
3. Settings opens over a paused flight, then a developer/purchase/consent sheet opens and closes: ad visibility must follow the top surface, not a stale screen callback. Pin in Task 3 and device-check Task 4.
4. High density, cutouts, ultrawide/resized windows, or a narrow safe frame: ads must not cover actions, enter gutters, or cause Next/Retry to move when a creative loads. Pin geometry in Task 3; inspect native coordinates in Task 4.
5. Billing/UMP/Publisher configuration is missing, revoked, or offline: preserve cached verified ownership, avoid fake prices/ads, keep play usable, and refuse enabled release exports with sample/missing IDs. Pin in Tasks 1–3 and export-check Task 4.

## Task 1: Complete purchase verification and acknowledgement in the existing Worker

**Files:** Create `server/src/google.ts`, `server/src/purchases.ts`, `server/test/worker/purchases.test.ts`. Modify `server/src/http.ts`, `session.ts`, `verify.ts`, `worker.ts`, `env.ts`, and `server/README.md`; retain existing session verifier tests.

**Interfaces:**

- `serviceAccountAssertion(accountJson: string, scope: string): Promise<string>` in `google.ts` extracts only the existing RS256 JWT signing algorithm. Both Integrity and Publisher token exchanges use it; preserve Integrity's current scope and diagnostic behavior.
- Move `limitAuth(request: Request, env: Env): Promise<void>` from `session.ts` to `http.ts`, preserving both existing session callers and behavior.
- `postAdFreePurchase(request: Request, env: Env): Promise<Response>` is the handler for `POST /purchases/ad-free`. It accepts `{purchaseToken: string}` only as required input; maximum token length 2048 and raw body 4096 bytes.
- Success: `200 {"ad_free":true}`. Pending: `202 {"pending":true}`. Invalid/unrecognized token or wrong product: `404 {"error":"...","code":"purchase_invalid"}`. Verified cancellation/refund: `409 {"error":"...","code":"purchase_inactive"}`. Invalid input: 400/413. Rate limit: 429. Malformed Google data, authorization/configuration failures, transport failures, or unresolved acknowledgement: sanitized 503. All failures have an `error` message; only authoritative purchase rejections have the stable purchase codes. A generic 404/409 from an old route, gateway, or deployment must not clear cached ownership.

  - `restores an already acknowledged purchase`: the same success, without another acknowledgement; repeated verification is valid.

## Execution order and review gates

Tasks 1 and 2 have separate file ownership and no code dependency. Task 3 depends on their stable contracts, not a live account. Task 4 integrates all of them. Under subagent-driven execution, use bounded Haiku implementation slices by default, a fresh reviewer per completed task, and a final whole-branch review; the integration owner runs verification after each slice, not the workers mid-edit. Under native execution, implement the same ordered tasks in this worktree and use one fresh whole-branch reviewer before delivery.

The specification is approved; this written plan still requires user review and selection of execution method before product edits. Recommended method: **subagent-driven**, because SDK lifecycle, native/Godot transforms, and purchase acknowledgement cross independent boundaries where a missed invariant can show ads to a buyer or lose a paid entitlement.
